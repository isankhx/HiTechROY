# Архитектура и алгоритмы

Документ описывает, как устроен код: модули, потоки данных, машина состояний миссии, алгоритм разведения дронов, тепловая обработка, бортовой агент и симулятор. Протокол, HTTP API и форматы файлов — в [PROTOCOL_API.md](PROTOCOL_API.md), настройки — в [CONFIG.md](CONFIG.md), отказы — в [FAILURES.md](FAILURES.md).

## 1. Общая схема

```
                       ноутбук (сервер)                                     борт × 3
┌──────────────────────────────────────────────────────────┐      ┌──────────────────────────┐
│ run_server.py                                            │      │ board/agent.py           │
│  ├ server/hub.py      TCP 7700 ◄────── протокол кадров ──┼──────┼► net_loop / send_loop    │
│  │   Drone: телеметрия, кадры, команды, резерв движения  │      │  telem_loop  ──► rospy   │
│  ├ server/mission.py  машина состояний, назначение задач │      │  rgb_loop    ──► камера  │
│  │   ├ server/traffic.py   шаги, дистанция, объезды      │      │  thermal_loop ─► USB     │
│  │   ├ server/thermal.py   проекция, тепловая карта      │      │  cmd_loop    ──► navigate│
│  │   ├ server/vision.py    YOLO по фото                  │      │  watchdog    ──► hold/land│
│  │   └ server/record.py    запись runs/<дата>/           │      └──────────────────────────┘
│  ├ server/web.py      HTTP 8080: SSE, MJPEG, команды     │
│  └ server/sim.py      виртуальные дроны (--sim)          │      board/protocol.py — общий
│  web/  index.html, app.js, style.css (без сборки)        │      board/thermal_drivers.py
└──────────────────────────────────────────────────────────┘
```

Принципы:

- **Один источник команд на борт.** Борт сам подключается к серверу; новое подключение с тем же `id` заменяет старое; второй `agent.py` на борту не стартует (flock).
- **Сервер ведёт дронов короткими шагами** (0.5 м), а не отдаёт маршрут целиком: так дистанция проверяется перед каждым шагом, а остановка — это просто отсутствие следующего шага.
- **Борт защищён без сервера**: сторож связи и сторож дистанции работают локально.
- **Симуляция и реальный режим используют один и тот же код сервера.** Симулятор подключается по тому же TCP-протоколу. В `--sim` порт бортов слушает только 127.0.0.1, поэтому настоящий дрон к такому серверу не попадёт.
- **Время.** `server/clock.py`: `now()` = `monotonic × SCALE`. `SCALE > 1` только в симуляции (`--speed`). Всё, что сравнивает длительности на сервере, использует `clock.now()`; метки времени в записях — `time.time()`.

## 2. Модули сервера

### `run_server.py`

Точка входа. Читает `config.json`, карту меток (`server/field.py`), создаёт `Hub`, детектор (`YoloDetector`, в симуляции без весов — `SimDetector`), `Mission`, запускает TCP-хаб, цикл миссии, при `--sim` — виртуальные дроны, затем uvicorn с FastAPI-приложением.

### `server/hub.py` — связь с бортами

`Hub.start` открывает `asyncio.start_server`. На каждое подключение `_client`: ждёт `hello`, находит `Drone` по `id`, затем в цикле читает кадры и вызывает `_dispatch`:

| тип | действие |
|---|---|
| `telem` | сохраняется в `drone.telem`, обновляется `t_telem`, `last_pos`, след `trail`; детектор скачка позиции (> 0.8 м за < 0.6 с → `jump_t`) |
| `rgb` | последний JPEG в `drone.rgb`, будятся MJPEG-клиенты (`rgb_cond`) |
| `thermal` | `t_thermal`, кадр передаётся в `Mission.on_thermal` |
| `ack`/`photo` | резолвится ожидающий `Future` из `pending[req]`; отрицательный `ack` сохраняется в `last_fail`, для `goto` сбрасывается точка шага и ставится пауза 1 с |
| `log` | строка в журнал сервера |

`_heartbeat` каждые 0.2 с шлёт всем `hb` с позициями соседей и дистанцией `guard`.

Свойства `Drone`, на которых держится логика:

- `connected` — есть сокет и данные были < 3 с назад;
- `fresh` — телеметрия моложе 1 с;
- `pos` — текущая позиция, если свежая и конечная, иначе последняя известная (для разведения нужна хоть какая-то);
- `locked` — `map_age < 1 с` (позиция по меткам свежая);
- `flying` — `armed` (если телеметрия свежая) или последняя высота > 0.3 м;
- `controllable` — можно слать `goto`: связь, свежая телеметрия, в воздухе, OFFBOARD, не пульт, не исключён, не потерял метки.

### `server/mission.py` — машина состояний

```
idle ──start──► takeoff ──все нашли метки──► survey ──облёт и осмотры завершены──► return ──все сели──► done
                   │                            │                                   ▲
                   └──────── «Домой» ───────────┴───────────────────────────────────┘
          «ПОСАДИТЬ ВСЕХ» из любой фазы ──► aborted ──все сели──► done
```

`Mission.run` — цикл 10 Гц: `tick()` → `_watch()` (отказы), подтверждение аномалий (`mapper.promote`), фаза, `traffic.tick`, `keep_clear`, метки состояния, публикация.

**takeoff.** Дроны по приоритету с интервалом `takeoff_stagger_s` получают `takeoff` (борт: `navigate(body, z, auto_arm)`). Дрон считается готовым, когда `locked` и высота > 0.4 м; его позиция в этот момент — `home` (место посадки). Нет захвата за `lock_timeout_s` или борт отклонил взлёт — дрон садится и исключается. Когда никого в `takeoff` не осталось: если T1 исключён → `return`; иначе `plan_survey` строит галсы, T1 получает маршрут `survey`, фотодроны — подъём на крейсерскую высоту (`park`).

**survey.** T1 едет по галсам. `on_thermal` обрабатывает кадры только при `tag == 'survey'` и высоте около `thermal.alt_m` (кадры на подъёме и при объездах на другой высоте в карту не идут, но записываются). `_inspections`: свободный фотодрон (не движется, камера жива) берёт ближайшую аномалию из `pending`, отфильтровав точки на пути T1 (`thermal_path`) и занятые другими; строит маршрут «подняться на крейсер → над точкой → снизиться на `photo_alt_m`»; стадии `fly → settle → photo → done`. Пока летит, цель уточняется, если оценка сместилась > 0.15 м. После съёмки — подъём на крейсер, `park`. Облёт завершён, когда у T1 кончился маршрут: T1 летит домой и садится, а фаза переходит в `return`, когда очередь пуста и никто не осматривает.

**return.** Все управляемые получают `home` (на текущей высоте, `homing=True` позволяет подлетать к севшим), по прибытии — `land`. `done`, когда все члены исключены (т.е. сели) и никто не в воздухе.

**_watch** (каждый тик, для каждого члена): нет телеметрии > 7 с → исключить; пульт → исключить; разоружён в полёте → исключить; батарея < 3.4 В → домой; метки потеряны > 2 с или скачок → `hold`, `lock_lost`; > 10 с без меток → `land`. Плюс тепловизор мёртв 5 с → предупреждение; лимит времени миссии → `return`. Исключённый дрон (`excluded`) больше не получает команд, но его позиция участвует в разведении как препятствие.

Приоритеты (`drones[].priority`): кому уступают дорогу и кто взлетает первым. T1 > T2 > T3.

### `server/traffic.py` — разведение дронов

Величины: `R` — радиус дрона; `guard = 2R + min_gap` — жёсткий предел (используется бортом); `D = guard + position_margin` — рабочая дистанция сервера; `guard_landed = 2R + 0.1` — к **севшему** дрону (борт получает его в `hb`, сервер применяет при возврате домой). По умолчанию 0.28 / 1.06 / 1.16 / 0.66 м.

`Motion` — состояние движения одного дрона: оставшийся маршрут `route`, текущая точка шага `sp` (куда послан setpoint), скорость, `final`, флаги блокировки, `retry_after`.

`Traffic.tick` для каждого управляемого дрона по убыванию приоритета:

1. Маршрут пуст → ждём прибытия к `final` (0.18 м в XY, 0.2 м по Z) или 8 с → `arrived`.
2. Шаг ещё выполняется (`now < eta`) → ждём. Если прошло 3 с после расчётного прибытия, а дрон далеко от `sp` → `sp` сбрасывается и шаг строится заново от реальной позиции.
3. `target = toward(origin, route[0], step_m)` — следующий шаг длиной ≤ 0.5 м.
4. `conflicts(dr, target)`: отрезок `pos→target` ближе `D` к резерву любого другого дрона (его `pos→sp`, или точка, если тот не управляем). Исключение: если уже ближе `D`, разрешено движение, не уменьшающее дистанцию (выход из клинча). К неуправляемым (севшим) при `homing` требуется только `2R + 0.1`.
5. Нет конфликтов → `goto`, `sp = target`. Иначе дрон стоит и:
   - стоящий без дела дрон на пути → ему `request_yield` в `free_spot` (ближайшая точка в поле, вне защищённых полилиний и чужих резервов, поиск по кольцам 0.6…3.5 м);
   - препятствие неуправляемое → если сама точка маршрута слишком близко к нему, отрезок укорачивается (`pull_back`); иначе через 1 с вставляется точка объезда (`detour`: перпендикулярно линии движения на `D + 0.2…0.8` м); если объезда нет → точка пропускается;
   - блокирует более приоритетный, который тоже ждёт, или ждём > 8 с → отходим в `free_spot`;
   - 20 попыток подряд → точка пропускается;
   - если пропускается **место посадки** (маршрут `home`), вместо пропуска выбирается ближайшее свободное место и дрон садится там.

`keep_clear` раз в секунду отгоняет стоящих без дела дронов, которые оказались ближе `D + 0.1` к пути (2.5 м вперёд) занятых.

Чего алгоритм не делает: не планирует глобально, не учитывает высоту (пролёт над другим запрещён вообще), не гарантирует живость при трёх взаимно блокирующих дронах (разрешается пропуском точек).

### `server/thermal.py` — тепловая карта и аномалии

Вход: кадр `h×w` (любой размер, любые единицы), поза камеры `x y z roll pitch yaw` (камера смотрит вниз, верх кадра = нос дрона после `rotate/flip`), позиции других дронов.

1. `orient` — поворот/отражение в конфигурации. `downsample` до ≤ 80×60 (крупные USB-камеры).
2. Фон = **медиана кадра**; `dT = кадр − фон`. Абсолютные градусы не нужны.
3. `project`: лучи пикселей (по `hfov/vfov`) поворачиваются матрицей `Rz(yaw)·Ry(pitch)·Rx(roll)` и пересекаются с плоскостью `z = target_height_m`. Кадры с креном > `max_tilt_deg` или высотой < 0.5 м не используются.
4. `_mask_drones` — пиксели, смотрящие на другие дроны (их след на земле радиусом `R + 0.2`, а для летящих ниже — их корпус), исключаются: горячие моторы не должны стать аномалией.
5. Тепловая карта: `dT` интерполируется в `k` раз (чтобы размер пикселя на земле ≈ `grid_cell_m`), раскладывается в сетку `sum/cnt` 5 см. Отображается среднее по наблюдениям в шкале `display_range`.
6. Детекция на исходной сетке: `dT ≥ threshold`, 4-связные компоненты ≥ `min_pixels`; центр — взвешенный по `dT`. Погрешность `err = 0.1 + размер пикселя + alt·tan 2°`.
7. `_merge`: компонента сливается с аномалией ближе `merge_radius_m`; координата — взвешенное среднее по пику `dT`; хранится кадр с максимальным пиком.
8. `promote` (из `Mission.tick`): `new → confirmed`, когда наблюдений ≥ `confirm_observations` **и** объект уже вышел из кадра на 1 с (или ≥ 20 наблюдений). Так дрон-осмотрщик получает уточнённую координату, а не первый взгляд с края кадра.

Статусы аномалии: `new → confirmed → assigned → inspected | ignored | photo_failed | unreachable | not_inspected`.

### `server/vision.py`

`YoloDetector` — Ultralytics, имена классов из весов, аннотированный JPEG через PIL. `SimDetector` — цветовые пятна для сцен симулятора, явно помечен «не YOLO». Классы из `yolo.ignore_classes` (по умолчанию `drone`) делают аномалию `ignored`.

### `server/record.py`

Папка `runs/<ГГГГММДД-ЧЧММСС>[-sim]/`: события, телеметрия 2 Гц, все сырые тепловые кадры (`thermal.f32` + индекс `thermal.jsonl`), фото, `anomalies.json`, `config.json`. Форматы — в PROTOCOL_API.md.

### `server/web.py`

FastAPI. Состояние — SSE `/api/events` (события `state` 5 Гц, `heat` 1 Гц, `trails` 0.5 Гц, `thermal` 5 Гц, `log`). Видео — MJPEG `/api/video/{id}`. Команды — POST. Инжекция отказов — только когда передан `world` (симуляция).

### `server/sim.py`

`World` — поле, нагретые объекты (гауссовы пятна), ссылки на дронов, `inject`. `SimDrone` — кинематика первого порядка к setpoint-у с интерполяцией по скорости, сторож связи и дистанции как у настоящего борта, телеметрия 10 Гц, тепловые кадры 6 Гц через ту же `project`, RGB-рендер поля с метками и объектами (PIL). Не аэродинамическая модель: нет инерции, ветра (кроме инжектированного), задержек PX4.

## 3. Борт: `board/agent.py`

Потоки (`threading`, Python 3.6+, только stdlib + rospy):

| поток | что делает |
|---|---|
| `net_loop` | подключается к серверу, шлёт `hello`, читает кадры → `on_msg` |
| `send_loop` | отправляет очередь: управляющие сообщения без потерь, `telem/rgb/thermal` — только последний (слоты) |
| `telem_loop` | `get_telemetry(aruco_map)` 10 Гц, следит за `armed/mode`: смена режима с пульта в полёте → `manual` |
| `rgb_loop` | последний `CompressedImage` с камеры, ≤ `rgb_fps` |
| `thermal_loop` | драйвер из `thermal_drivers.py`, переподключение при ошибке |
| `cmd_loop` | `takeoff` → `navigate(body, auto_arm)`, `goto` → `navigate(aruco_map)` после проверки сторожа, `hold` → `navigate(body, 0,0,0)`, `land` |
| `watchdog_loop` | нет `hb` 1.5 с → `hold`; 6 с → `land`; сосед ближе `guard` и мы к нему летим → `hold` |

Правило пульта: если в полёте `mode` не OFFBOARD/AUTO.LAND, агент не шлёт ничего до разоружения. Программа никогда не возвращает OFFBOARD принудительно.

`thermal_drivers.py`: `mlx_serial` (GY-MCU90640, поток `5A 5A`, контрольная сумма, автоопределение порядка байт), `serial_csv` (строка чисел), `uvc` (веб-камера, серые уровни), `uvc_split16` (16-бит температуры в нижней половине YUYV-кадра). Последовательный порт — через `termios`, без pyserial.

## 4. Интерфейс: `web/`

Без сборки и зависимостей. `app.js`: `EventSource` → состояние; карта на `<canvas>` (слои: тепло, метки, маршруты, следы, зоны); камеры — `<img src=/api/video/..>`; тепловой кадр — canvas с палитрой; модальное окно аномалии; панель отказов появляется, если `/api/sim/faults` отвечает `enabled`.

## 5. Тесты

- `tests/test_real_mode.py` — сервер в **реальном** режиме + три настоящих `board/agent.py` поверх `tests/fake_ros.py` (подмена `navigate/get_telemetry/land`, камеры и тепловизора). Сценарий: потеря меток у T2, обрыв связи с T3, проверка минимальной дистанции и завершения.
- `tests/test_faults.py` — все сценарии из FAILURES.md на симуляторе.
- Ручной прогон: `python run_server.py --sim --speed 3`.
